# Discussion: Google Cloud Dataflow vs. Event-Driven Microservices
### 1. Architectural Overview
Preprocessing IoT and smart meter measurements involves streaming ingestion, missing-value filtering, unit conversion, and loading into analytics storage like BigQuery. In previous milestones, this was implemented as a unified pipeline using Google Cloud Dataflow (Apache Beam). In Milestone 4, the same pipeline is realized using decoupled, event-driven microservices (`FilterReading` and `ConvertReading`) communicating through a shared Google Pub/Sub topic with message attribute filtering.
### 2. Google Cloud Dataflow: Advantages & Disadvantages
Google Cloud Dataflow provides a fully managed, serverless unified stream and batch processing platform. Its primary advantage is end-to-end operational simplicity with automatic worker scaling, exactly-once processing semantics, and native support for complex windowing and aggregations without needing container orchestration. However, its disadvantage lies in tighter coupling and pipeline rigidity: the entire processing logic must be authored within the Apache Beam SDK, debugging distributed pipeline steps can be cumbersome, and updating a single step (such as changing a conversion formula) typically requires updating and redeploying the entire streaming pipeline job.
### 3. Event-Driven Microservices (Pub/Sub + GKE): Advantages & Disadvantages
The event-driven microservice approach excels in modularity, flexibility, and independent lifecycle management. Each processing phase exists as an isolated containerized service that can be written in any language, scaled independently according to compute demands, and updated with zero downtime to other stages; downstream consumers can also easily tap into intermediate events via filtered Pub/Sub subscriptions. On the other hand, its disadvantage is increased architectural overhead and latency: passing records back and forth across a single Pub/Sub topic introduces multiple network hops, requires managing Kubernetes cluster infrastructure, and places the burden of message deduplication, at-least-once handling, and dead-letter queues on the application developer.
### 4. Conclusion & Recommendation
Dataflow is the optimal choice for high-throughput, latency-critical data engineering pipelines focused solely on linear ETL and heavy analytics aggregation. Conversely, an event-driven microservices architecture is superior when business logic changes frequently, when individual steps must be reused across different systems, or when distinct teams own separate processing responsibilities within a broader distributed system.
